[[covert-side-channels]]
=== Covert and Side Channels

[[threat-model]]
==== Threat model

The confidentiality assets considered in this guide are data or activity that a
system policy permits within one security domain but forbids another domain from
learning. In this guide, a *security domain* is an entity or group of entities
that the policy treats as a distinct unit of trust and protection. A process,
privilege mode, sandbox, guest, ASID, VMID, or SDID may identify or help enforce
a boundary, but none defines a security domain by itself.

This discussion trusts the processor's architecturally specified access controls
and the privileged software that assigns and switches security domains. The
model assumes that they enforce ordinary functional isolation. It then asks
whether timing-dependent implementation effects can reveal information across
the policy boundary. The attacker may run untrusted code only at privilege
levels allowed by the platform. Typically, the attacker controls only an
unprivileged application. Other threat models may allow the attacker to control
code inside a virtual machine or sandbox, but not the host operating system or
hypervisor.

Security domains can interact through two distinct kinds of timing channel:

* In a *sequential/residual-state* channel, a source domain changes the state of
  a resource. After a domain switch, a receiver uses that resource and observes
  the state left behind. Cache contents, predictor history, and reused buffers
  are examples. This channel requires suitable scheduling and resource reuse,
  but not simultaneous execution.
* In a *concurrent/contention* channel, a source and receiver execute during
  overlapping intervals and contend for a shared resource. This channel
  requires suitable scheduling, placement, shared hardware, and timing
  resolution. Sequential state reuse alone does not establish concurrent
  contention.

A local software attacker needs a way to measure time or compare execution
progress, such as an accessible clock or counter. A remote attacker instead
needs a repeatable interaction whose response time remains distinguishable
through network noise. Power, electromagnetic, acoustic, and other physical
measurements require physical access and separate measurement models. These
capabilities do not imply one another. Every security claim must state the
observations, attacker placement, and number of repetitions it assumes.

[NOTE]
.Scope and non-goals
====
Timing fences do not universally prevent Spectre or replace constant-time
programming.
This guide also makes no claim that they mitigate power or electromagnetic
attacks. Such claims require a platform-specific threat model and mechanisms
beyond local timing isolation.
====


==== Definitions

A channel exists when information can cross a security boundary through an
observable effect. For example, a channel could allow a user-mode process to
learn a value used by a supervisor-mode operation. The
<<glossary-roles,roles of the sender, receiver, and victim>> determine whether a
mechanism is a covert channel or a side channel:

* In a <<glossary-covert-channel,*covert channel*>>, an attacker-controlled
  sender and receiver collude to encode and decode a value.
* In a <<glossary-side-channel,*side channel*>>, a victim unintentionally
  creates a signal from secret-dependent behaviour, and an attacker controls
  the receiver.

Demonstrating a covert channel does not by itself demonstrate a side-channel
vulnerability. A side-channel demonstration also needs a victim whose
secret-dependent behaviour produces a distinguishable signal under the same
resource-sharing, scheduling, observation, and decoding conditions. Conversely,
ruling out communication between a colluding sender and receiver rules out
victim leakage only if the model covers the victim's possible behaviour and all
of the side-channel attacker's capabilities. A result obtained with restricted
clocks, placement, or resource sharing supports only a claim with those same
restrictions.

Information can be carried by power or electromagnetic signals, by the duration
of an operation, or by the time required to use a shared resource. This guide
focuses on timing channels.

==== Architectural and microarchitectural timing

An *architectural timing channel* exists when architecturally specified program
behaviour depends on a secret and changes observable execution time. Examples
include branching on the secret, performing a secret-dependent amount of work,
or using an instruction whose specified latency depends on its operands. This
is ordinarily considered a software property.
Security-sensitive software should avoid it when its threat model requires
behaviour independent of secret data.

A *microarchitectural timing channel* exists when execution changes
microarchitectural state that later affects an observable latency, even though the
architectural result remains correct. Caches, predictors, queues, and buffers
can retain such state after committed or transient execution. For example, a
fixed instruction sequence may use a secret-dependent load address to select a
cache line, causing a later access to be faster or slower. Cache
observation is illustrated in <<example-cache>> and in Flush+Reload experiments.
cite:[flushreload2014]

[NOTE]
.Constant-time and data-independent execution
====
Constant-time programming is a method for making a specified program behave
independently of secret data under a stated compiler, platform, and observation
model. In this guide, *data-independent execution time* means that execution
time may vary with public inputs or environmental conditions, but not with
secret data when those other conditions remain fixed. This is usually what
"constant time" means; it does not require identical elapsed time on every run.
Neither term automatically covers every microarchitectural effect, remote
observer, or physical measurement. The observation model remains essential.
====

==== Measuring time

Observing a timing channel requires a measurement method, and the available
methods depend on the implementation and platform. A
<<glossary-pmu,performance monitoring unit (PMU)>> may expose counters or
timing-related events, but the platform and privileged software control their
availability, virtualization, filtering, and state across a domain switch. The
model therefore neither assumes that a receiver can observe a counter across a
security boundary nor assumes that counters are unavailable to an attacker.

Restricting or partitioning <<glossary-pmu,PMU>> access can remove one
measurement method, but it does not remove every timer. Depending on the
platform and threat model, an attacker may compare progress through an
accessible clock, repeated interactions, or another shared observable. Remote
and physical measurements require their own models; local <<glossary-pmu,PMU>>
access does not imply them.
